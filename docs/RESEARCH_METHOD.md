# Research Method

## 1. 운영 원칙

범위가 명확한 질문 하나를 실행 가능한 실험으로 정의합니다.

- 초기에는 활성 실험을 1개로 제한합니다.
- 기존 프로젝트 전체를 복제하지 않고 기술적 문제를 실험 단위로 분리합니다.
- 기존 경험은 기여 범위와 근거로 기록하며, 필요한 연구 질문에 대해 재구현합니다.
- 실험별 독립 실행을 우선합니다.
- 공통 모듈은 실제 공유 필요가 확인될 때 추출합니다.
- 템플릿은 판단과 재현에 필요한 최소 항목으로 유지합니다.

## 2. 실험 흐름

1. 질문·가설·범위를 정한다.
2. Baseline 또는 기준 조건을 정한다.
3. 입력 데이터, 환경, 평가 지표, 허용 오차를 정한다.
4. 구현 또는 재현 절차를 준비한다.
5. 조건을 기록하며 실행·측정한다.
6. 결과, 해석, 한계, 실패 원인을 정리한다.
7. PR에 변경과 검증 이력을 연결한다.

비교 실험에서는 변경 변수와 통제 조건을 명시합니다.
결과를 본 뒤 조건이나 지표를 변경하면 변경 이유와 이전 조건을 보존합니다.

## 3. 최소 실험 계획

실험을 시작하기 전에 다음 항목을 작성합니다.

- 식별자: 주제 ID, 실험 ID, 관련 Issue
- 질문·가설·범위
- Baseline 또는 기준 조건
- 데이터·환경·장비
- 변경 변수와 통제 조건
- 평가 지표·반복 조건·허용 오차
- 완료 기준과 예정 산출물

실물 실험은 장비 가용 여부, 동작 범위, 힘·속도 제한,
중단 조건을 해당 실험에 맞게 추가합니다.

## 4. 개발 환경과 의존성

다음은 사용자 제공 기술 스택과 환경 계획입니다.
각 실험의 설치·동작·호환성이 검증되었다는 의미는 아닙니다.

| 구분 | 환경·도구 |
|---|---|
| 문서·경량 개발 | macOS, Apple Silicon, VS Code + Codex, Git/GitHub |
| 알고리즘 | Python, NumPy, SciPy, OpenCV, Matplotlib, pytest |
| 선택 언어 | ROS 2 또는 성능 요구에 따른 C++ |
| 로보틱스 | Ubuntu 24.04 LTS, ROS 2 Jazzy, CycloneDDS, MoveIt 2, Nav2, AMCL |
| 시뮬레이션 | NVIDIA Isaac Sim |
| 장비 후보 | Doosan M0609, OnRobot RG2, RGB-D 카메라 및 관련 센서 |
| Vision·Learning | PyTorch, Ultralytics YOLO, MediaPipe, OpenCV |
| 애플리케이션 | FastAPI, React/TypeScript, PyQt5, PostgreSQL |
| 인터페이스 | HTTP, WebSocket, ROS 2 Topic·Service·Action |
| 실행·자동화 | Docker, GitHub Actions |

환경 관리 규칙:

- 실험에 필요한 의존성만 설치합니다.
- 실험별 Python 가상환경과 의존성 잠금 파일을 사용합니다.
- 모든 기술을 하나의 대규모 통합 requirements.txt에 넣지 않습니다.
- ROS 2·Isaac Sim·GPU 관련 버전과 호환성을 실험별로 기록합니다.
- 사용자 제공 환경 구분인 NetClean의 Isaac Sim 5.1과 다른 실험의 6.1을 별도로 취급합니다.
- 실제 설치 버전과 호환 여부는 각 환경에서 확인하여 기록합니다.
- GPU가 없는 macOS에서도 가능한 순수 알고리즘 시험·분석 경로를 분리합니다.
- 소프트웨어, 시뮬레이션, 실제 로봇 실행 절차를 구분합니다.

장비의 정확한 사양과 가용 여부는 실험 착수 시 확인합니다.

## 5. 폴더와 식별자

문서와 GitHub 템플릿 외에 다음 경로는 해당 연구·실험을 시작할 때 필요한 부분만 추가합니다.

```text
docs/
└── topics/
    └── <topic-id>/
        └── README.md

experiments/
└── <topic-id>/
    └── <experiment-id>/
        ├── README.md
        ├── src/
        ├── configs/
        ├── tests/
        ├── scripts/
        ├── environment/
        └── data/

results/
└── <topic-id>/
    └── <experiment-id>/
        └── <run-id>/
            ├── manifest.yaml
            ├── config.yaml
            ├── metrics.json
            ├── report.md
            ├── logs/
            └── figures/
```

- `topic-id`: 로드맵의 R01~R09.
- `experiment-id`: 주제 내 개별 질문을 식별하는 안정적인 이름.
- `run-id`: UTC 기준 `YYYYMMDDTHHMMSSZ-<짧은커밋SHA>-<고유접미사>`.
- experiment README: 질문, 기준 조건, 환경 준비, 실행·평가 명령, 결과 링크.
- environment: 환경 명세와 잠금 파일.
- data: 작은 합성 데이터 또는 데이터 취득·복원 안내.
- tests: 해당 알고리즘의 정확성 등을 확인하는 데 필요한 시험.

실험별 내부 구조는 Python·ROS 2 등 실행 방식에 맞게 조정할 수 있습니다.
빈 디렉터리와 모든 주제 폴더를 미리 생성하지 않습니다.

## 6. 실행 결과의 최소 기록

### manifest.yaml

- 실행 ID와 시간대가 포함된 시작·종료 시각
- 구현을 포함한 코드의 전체 Commit SHA
- 작업 트리 변경 여부와 필요한 변경분
- OS, CPU/GPU, 메모리 및 사용 장비
- 언어·의존성·ROS 2·시뮬레이터 등 실제 사용 버전
- 환경 명세·잠금 파일 식별 정보
- 입력 데이터 버전·SHA-256 및 분할 정보
- 정확한 실행·평가 명령과 실행 디렉터리
- 랜덤 시드와 재현에 영향을 주는 실행 설정
- 성공·실패·중단 상태

### config.yaml

실행에 실제 적용된 전체 설정을 보존합니다.
기본값도 포함하고, 원본 설정과 실행 시 덮어쓴 값을 반영합니다.
비밀값은 기록하지 않습니다.

### metrics.json

- 지표명, 값, 단위
- 평가 대상과 표본 수
- 반복 횟수·시드
- 집계 방법과 필요한 변동 정보
- 비교 대상 실행 ID

실패·중단으로 측정하지 못한 값은 이유와 함께 기록합니다.
측정하지 못한 값을 0으로 대체하지 않습니다.

### report.md

- 질문과 실행 조건 요약
- 주요 결과와 비교 실행 ID
- 사전 목표의 달성 여부
- 해석, 한계, 실패·중단 원인
- 재현 확인 상태
- 관련 Issue·PR 및 외부 산출물 링크

재실행은 새로운 실행 ID를 사용합니다.
기존 실행의 원본 지표·로그를 덮어쓰지 않습니다.
보고서를 정정하면 변경 이력을 남깁니다.

## 7. 데이터와 대용량 산출물

Git에 저장할 항목:

- 연구 문서와 구현 코드
- 실험 설정 YAML/JSON
- 작은 합성 테스트 데이터
- 평가 지표 CSV/JSON
- 결과 요약, 비교 그래프, 대표 이미지
- 재현용 실행·평가 스크립트

기본적으로 Git 추적에서 제외할 항목:

- ROS 2 Bag과 대형 센서 데이터
- 학습 데이터셋과 모델 가중치
- Isaac Sim USD 및 대용량 에셋
- 장시간 영상과 대형 실행 로그

처음에는 Git과 GitHub로 관리 가능한 소규모 실험부터 진행합니다.
필요할 때 Git LFS, GitHub Releases 또는 외부 저장소를 검토합니다.

외부 산출물에는 저장 위치, 버전, SHA-256,
취득·복원 방법과 필요한 접근 조건을 기록합니다.

공개할 수 없는 원본 대신 독립적인 합성 데이터를 사용할 수 있습니다.
이 경우 합성 데이터의 생성 조건과 실제 데이터와의 차이를 설명합니다.

## 8. 공개 및 민감정보 관리

- .env, API 키, 토큰, 비밀번호, 내부 네트워크 설정은 추적 대상에서 제외합니다.
- 얼굴·음성·개인 식별 데이터는 공개 권한 확인 전 업로드하지 않습니다.
- 팀 내부 문서와 비공개 데이터는 별도 승인 없이 공개하지 않습니다.
- 로봇 하드웨어 설정·좌표값은 안전성과 공개 적절성을 검토합니다.
- 외부 논문·코드·데이터·에셋의 출처와 라이선스를 기록합니다.

## 9. GitHub 기록 체계

### Issue

하나의 연구 질문 또는 범위가 명확한 실험을 관리합니다.

최소 항목:

- 배경·출처와 관련 주제 ID
- 질문·가설·범위
- Baseline·데이터·환경
- 평가 지표와 완료 기준
- 진행 중 판단·변경 사유
- 결과·PR 링크

필요하면 상위 연구 Issue와 개별 실험 Issue를 연결합니다.
[연구 질문 템플릿](../.github/ISSUE_TEMPLATE/research.md)과
[실험 템플릿](../.github/ISSUE_TEMPLATE/experiment.md)을 사용합니다.
초기 유형 라벨은 필요할 때 type:docs, type:research, type:experiment로 시작할 수 있습니다.

### Milestone

관련 Issue를 산출물 중심으로 묶습니다.
문서 기반 정리 또는 특정 주제의 명세·비교 실험·보고서 등을 단위로 삼습니다.

Milestone 완료율과 연구 성능·재현 검증 상태는 별도로 기록합니다.
일정은 실제 가용 시간과 장비를 확인한 뒤 정합니다.

### Pull Request

[PR 템플릿](../.github/pull_request_template.md)에 다음을 기록합니다.

- 관련 Issue와 변경 이유
- 구현·문서·설정의 변경 범위
- 검증 환경과 명령
- 실행 ID·결과 경로·핵심 결과
- 한계·미해결 사항
- 필요할 때 개인 기여 기록의 변경 근거

진행 중인 Issue는 참조하고, 완료 기준을 충족한 PR에만 Closes 키워드를 사용합니다.
자동 종료 키워드는 기본 브랜치를 대상으로 하는 PR에서 작동합니다.
[GitHub 공식 문서](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

개인 연구에서는 자체 검토를 수행하고 검토 내용을 남깁니다.
문서 PR은 사실관계·링크·상태 일관성을 검토합니다.
구현 PR은 변경에 필요한 정확성 시험과 실행·평가 결과를 연결합니다.

확정한 방법과 결론은 저장소 문서에 반영하고,
Issue에는 그 판단에 이른 과정과 변경 이유를 남깁니다.

Issue·PR 템플릿의 자동 적용은 기본 브랜치에 반영된 후 사용할 수 있습니다.

## 10. 완료와 검증 상태

실험은 다음 조건을 모두 충족할 때 완료로 표시합니다.

1. 연구 질문·가설·범위가 문서화되어 있다.
2. Baseline 또는 기준 조건이 명시되어 있다.
3. 실행 가능한 코드 또는 재현 절차가 존재한다.
4. 실험 환경·설정·입력 데이터가 기록되어 있다.
5. 사전에 정한 평가 지표로 결과를 측정했다.
6. 결과·해석·한계·실패 원인을 기록했다.
7. GitHub PR에 구현 또는 재현 절차와 검증 이력이 연결되어 있다.

가설이 기각되거나 성능이 개선되지 않아도
실험 절차와 분석을 완료하면 연구 완료로 기록할 수 있습니다.

다음 상태는 독립적으로 관리합니다.

| 항목 | 기록 예 |
|---|---|
| 실험 완료 | 미완료 / 완료 |
| 목표 성능 | 기준 미정 / 미평가 / 달성 / 미달 |
| 동일 환경 재현 | 미검증 / 성공 / 실패 |
| 타 환경 재현 | 미검증 / 성공 / 실패 |
| 실제 하드웨어 검증 | 미수행 / 통과 / 미통과 / 해당 없음 |

재현 성공을 표시하려면 다음을 확인합니다.

- 동일 코드·실제 설정·입력 데이터를 식별할 수 있다.
- 환경과 의존성 버전이 기록되어 있다.
- 랜덤 시드와 필요한 실행 조건이 기록되어 있다.
- 문서의 절차로 재실행할 수 있다.
- 결과가 착수 전에 정한 허용 오차를 충족한다.
- 재실행 결과와 비교 근거가 연결되어 있다.

시뮬레이션 검증과 실제 로봇 검증 결과는 각각 기록합니다.
